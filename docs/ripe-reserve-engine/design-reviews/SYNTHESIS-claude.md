# Instant Bond Lane — six-memo synthesis

Six independent product-and-design reviews of PR #156's Instant Bond Lane, organized so a human can decide. Nothing here is a new review, a vote, or a go-live call. Counts are descriptive; silence is "no position."

**Sources.** The six memos as saved in `docs/instant-bond-lane/design-reviews/` on the `instant-bond-lane` worktree: A = Claude (`agent-claude.md`, the full review — the pasted version was only its recap), B = Codex, C = Grok, D = GLM, E = DeepSeek, F = Ox. B–F are byte-identical to the pasted memos apart from backtick escaping.

**Pins.** All six read commit `d136a262` (tree `2cdcdd6e`). None used `9b08846c`. The contracts are identical at both; `d136a262` rewrote owner decisions 8, 9, 11 and 14 to match the code (epoch length and payment token are governed; only `start` changes cadence; payment token swaps only while stopped). §6.7 and §5.1 did not change. A docs rewrite settles "the docs misdescribed the code"; it does not settle "the code should behave differently."

**Numbering reconciled at the pin.** A's "15 Aug owner decision (item 8)" is item 8 of the PR #156 owner-decision comment ("Bind expected core RipeGov vault ID and minimum actual lock"). E and F cite the same decision as spec decision 16 / the Rev-24 bullet "`buyNow` has no vault-ID or minimum-lock bindings." Same decision, two numberings. The Rev-24 record lists the reversal without a reason (A traces the removal to a "clean up" commit, `406265d6`); C reads decision 16's "Preview discloses that ID" as the recorded rationale and rejects it.

**Contract facts the memos rely on, confirmed at the pin.** `setCumulativeMinted` is an immediate (non-timelocked) Foxtrot call bounded only by `<= mintBudget`, so it can lower the counter to any value including zero. Override install and cancel are timelocked; `setCanBuyNow` and Department pause never touch `rateOverride`; `setConfig`/`start`/`stop` clear it. `test_preview_buy_races.py` pins that a previewed-unlocked buy settles locked if the live `minLockDuration` rises between preview and buy. No memo disputes any of these; D treats the counter behavior as acceptable, the others do not.

### Each agent's top 3

- **A** — (1) run the controller as a one-step ratchet by config (`minUp=maxUp`, `minDown=maxDown=decay`), add a stranding invariant, and treat the ceiling as the real control, re-ratcheted by governance against an off-chain reference [P1]; (2) "unlocked means unlocked" — one assert in `buyNow`, UI defaults unlocked, lock via Teller with the blended unlock shown [P1]; (3) de-sharpen the immediate levers — monotonic `setCumulativeMinted`, `setConfig` preserves the live `canBuyNow` ("sticky"), timelocked `start`/token swap, immediate cancel of an installed override [P2].
- **B** — (1) bind buyer settlement consent (B's P0 bundle: settlement mode, expected vault and lock range, blended unlock shown, `runId`/`configVersion`, payment token and recipient, `marketOpen` vs `settlementReady`, controller rate vs final rate and its source); (2) make the lifetime issuance cap real and the run finite (B's P0 bundle: remove runtime `setCumulativeMinted`, mandatory run end and `runId`, delayed reopen/token swap, immediate cancel of an unused override, reject locked buys during an exit freeze); (3) remove timing-weighted demand and unavailable-time decay.
- **C** — (1) bind unlocked vs locked (and, for locked, minimum actual lock and vault ID); (2) drop timing from the high-utilization step; (3) make the override die on pause or unused time.
- **D** — (1) add override expiry; (2) rename; (3) simplify or remove the timing signal (experiment first).
- **E** — (1) override freshness bound (expiry after N epochs); (2) `cumulativeMinted` one-way ratchet + timelocked setter; (3) gate the locked path off at activation, and say so.
- **F** — (1) delete amount-weighted timing; (2) override → bounded relative nudge with expiry; (3) rename.

### Each agent's biggest recorded-decision disagreement

- **A** — Rev-24 dropped the minimum-actual-lock binding the 15 Aug decision (item 8) selected, "with no recorded reason," and the tests pin the consequence: a previewed-*unlocked* buy can settle into a RipeGov lock with an 80% exit fee. A's "close second": §5.1 omits Olympus v1/Pro volume-only pricing, "whose measured Frax outcome is the strongest evidence about this design."
- **B** — Rev-24: a wallet quote can become a locked vault purchase (or a requested lock become wallet delivery) without buyer-bound consent; "Output slippage protection is not custody consent."
- **C** — Decision 18: keeping amount-weighted timing while the period price is fixed, after calling that timing strategically selectable — the recorded reason "treats last-block `minUpBps` as a calibration problem. It is a design problem."
- **D** — Decisions 21/§6.7: no override expiry; the "new state machine" reason is wrong — "it's one variable and one check."
- **E** — Decisions 21, 22 + §6.7: a timelocked exact pin is already stale by construction; letting it fire at an arbitrarily distant rollover compounds it.
- **F** — Decision 18: the manifest requires calibrating as if timing contributes nothing — "if the mechanism must be treated as contributing zero to be approvable, it can never be allowed to carry load, and it should not exist."

### Where they agree, where they split, and which splits come from different objectives

- **Unanimous (6/6):** support the concept; keep epoch-fixed pricing and lazy rollover; no separate vesting; rename away from "bond"; keep full-fill-only; keep the contract free of a RIPE fair-value oracle; the override needs changing in some way.
- **Near-unanimous:** the timing signal should go or be neutralized (A by config; B, C, F remove; D simplify-or-remove after an experiment; E keeps the controller whole and never singles timing out); `setCumulativeMinted` should be monotonic and/or timelocked (A, B, C, E, F; D keeps it); the unlocked-vs-locked settlement path should be bound on the buy (A, B, C; F — bindings *or* a UI consent chip; E adds the vault/min-lock pair only when the locked path re-enables; D silent); an override **expiry** (B, C, D, E, F) — with A the lone explicit dissent: keep no expiry for exactness, rely on an immediate cancel plus a hard reopen checklist.
- **Real splits:** *absolute pin* (A no expiry; D, E with expiry) vs *bounded nudge* (B, F relative ± bps with expiry; C prefers the nudge but accepts an exact rate that expires; A's glide-to-target variant as a P3 experiment); *cancel immediacy* (A, B, C immediate vs D, E, F timelocked); *pause disarms the override* (B, C) vs *pause leaves it* (A, D, E, F); *finite run end* (B) vs *no sunset* (A, C, D, E, F); *no decay during unavailable periods* (B) vs *decay as coded* (A, C; D, E, F silent); *gate the locked path off* (E) vs *bind it and keep it* (B, C, F) vs *de-emphasize via UI default + Teller route* (A) vs *keep as-is* (D); *per-address cap* (E experiment) vs *sybil-defeated, don't* (A).
- **Splits that trace to the assumed objective:** A's "issuance discipline first" is why A names the ceiling, not the controller, as the safety story and wants it re-ratcheted against a reference; B's reserves-per-dilution framing plus the ATM's finite authorization drives the run-end and `runId` proposals nobody else makes; D's and F's distribution framing is why D keeps the current shape and F prices the buyer-facing surface (bindings, name) higher; E's holder-base-health clause is the root of the per-buyer-cap experiment and the dilution-sizing questions; A, B and C each say their shape flips if the buyer or objective changes — A to a reference-priced sale if the buyer is arbitrageurs, B to a batch auction and C to an SDA/VRGDA if price discovery comes first. Note also a definitional split: E's rejected "simpler lane" is unlocked-only with **no override**, which is not the simpler lane A, B, C and F picked (all of those keep a changed override).

## 3. Product shapes

**Current lane as-is (picked by D, E).** D: the epoch-fixed controller is the right shape for distribution; only the override needs a fail-safe expiry, and timing is the first simplification candidate. E: the controller is the product; what it needs is "honesty at the edges" — a fresh override, a hard counter, a truthful lock, a truthful name — plus two experiments (per-buyer cap, early rollover).

**Simpler lane (picked by A, B, C, F).** A: same skeleton and clock; controller collapsed by config to one up-step and one down-step equal to decay with a stranding invariant; the ceiling set as the price the treasury will actually accept and re-ratcheted by governance against an off-chain reference; lock opt-in via a UI default and a Teller route; four immediate levers de-sharpened — "the three contract edits are each a few lines and none touches the settlement path." B: a finite "RIPE Reserve Sale" — utilization-only movement, no decay while unavailable, explicit settlement consent, a real lifetime cap with a run end, delayed and versioned reopening. C: a "standing tap" — utilization-only next rate, unlocked-vs-locked bound on the buy, manual price changes that expire or die on pause. F: its own "Shape B" — timing deleted, override a bounded relative nudge, renamed; no sunset kept.

**Different models considered (none picked).** A: a reference-priced sale (Olympus EM/CD shape) — "right model later, when a TWAP-grade reference exists; wrong model now," because RIPE's only on-chain source is one Aerodrome spot pool, manipulable in the cheap direction; kept as an off-chain monitoring experiment. B: uniform-price batch auction — pick only if large one-off size, competitive price discovery or pro-rata allocation outranks instant delivery and low operator touch. C: Bond Protocol-style sequential Dutch — only if intra-period discovery becomes the goal. D: VRGDA-style continuous price — rejected as harder to test and parameterize. E: epoch-close uniform-price batch — rejected because it destroys "instant." F: oracle-linked continuous drip (ATM-style) — rejected because it undoes the no-oracle decision. E separately rejects a *no-override* simpler lane because it removes the only human price intervention.

**Where the matrices agree (A, B, C, D, E, F).** Preview reports the projected epoch and rate (including an installed override, which preview does not consume), remaining epoch capacity, minimum payment, remaining mint budget, base/bonus/total RIPE, `actualLock` as the *deposit* duration, the current core RipeGov vault ID, and `canExitEarly`/`exitFee`/`isExitFrozen`. `available` is market-readiness only and never promised wallet balance, allowance, Endaoment liveness, Teller/vault admission, or RIPE pause/blacklist. Between preview and buy, capacity can be consumed by another buyer, the epoch can roll, immediate controls can flip, lock terms and the vault pointer can move, and an override can be installed or cancelled. Buy binds `expectedEpoch`, `minRipeOut`, `deadlineBlock` and the exact full-fill `paymentAmount`. Retry is re-preview and resend.

| Split | Positions |
|---|---|
| **Preview should also report** | A: epoch-end block and a pending-override flag (computable from `getEpochSnapshot()` + `rateOverride()`), revert reason codes, and the account-level post-deposit unlock (client-computed; preview is caller-agnostic). B: run/config identity, settlement mode, controller rate vs final rate and its source, projected *blended* account unlock. F: the blended unlock. E: an `unavailableReason` enum or prominent `remainingPayment`. C, D: as-is is a quote, not a reservation — fine. |

B: stop/restart can recreate the same epoch number with a new seed, token or config. E: an "impossible vault range" silently unlocks. | **Retry UX** | A: never auto-resubmit with a new epoch without re-showing the rate; one-tap resize to the new remaining amount; "epoch tail unbuyable, next epoch at block N"; on a lock-required revert, "a lock of N blocks is now required — confirm?" and resubmit with the explicit lock; hide the lock option when frozen and show the fee as "you keep X% of your whole position"; client pins the token address it previewed. Override lifecycles are under the override options in §4 and summarized here. Current behavior (all six agree): queue (timelocked; a *queued* action can be dropped immediately with `cancelPendingAction` — A) → install → consumed at the first later *successful* rollover regardless of elapsed epochs (a reverted purchase restores it — A) → cancel of an *installed* override (timelocked) → invalidated by `setConfig`/`start`/`stop`; pause and `setCanBuyNow` leave it in place. Proposed: A keeps no expiry, makes installed-override cancel immediate, allows install before the first epoch, and makes the reopen check a hard manifest item; D/E add an expiry (pause still preserves it); B/C add expiry *and* pause-disarm *and* immediate cancel; F adds expiry to a relative nudge (pause leaves it, it expires harmlessly); B alone adds a named target epoch and `runId`/`configVersion` matching.

## 8. Next conversation

### Decisions that need a human call

**1. Settlement consent on the buy (decision 16 / Rev-24).**
Options: (a) bind settlement mode — and for locked buys the vault ID and minimum actual lock — on `buyNow`; (a′) A's narrower version — one assert that a zero lock request cannot settle locked, no ABI change, with the UI defaulting to unlocked and routing locks through Teller; (b) gate the locked path off at activation and add the bindings only when it re-enables; (c) keep Rev-24 (disclosure only).
Support: (a) B, C, F (F alternatively accepts a UI consent chip); (a′) A; (b) E; (c) nobody argued for it — D is silent.
Strongest line for (a): "Disclosure is not a bind. The tests are the evidence." (C). For (a′): "the lane lock gives nothing a self-deposit does not," and the assert needs no ABI change (A). For (b): a lane that quotes a lock RipeGov's blend cannot honor "is selling a promise it can't honor" (E). For (c): the recorded reason — fewer bindings — which F calls "a simplicity win paid for by the buyer" and A calls "ABI minimalism under a size ceiling that Revision 24 itself dropped."

**2. The timing signal (decision 18).**
Options: (a) remove it from the contract; (b) neutralize by config (`minUp=maxUp`) and keep the code; (c) run the simulator experiment first, then decide; (d) keep it and treat catch-up as calibration.
Support: (a) B, C, F; (b) A; (c) D; (d) E — by implication of keeping the current controller, not an argued defense of the timing signal.
Strongest line for removing: "if the mechanism must be treated as contributing zero to be approvable, it can never be allowed to carry load, and it should not exist" (F). For neutralizing by config: the information "is real only when two or more bots are racing, and in that regime it rewards the race" — and equal endpoints are already an explicitly valid config (A). For experiment-first: the `minUpBps` floor is the safety boundary either way — keeping the signal "doesn't create a safety problem" and removing it "loses information but not safety" — so run the simulator and "if it's not materially better, remove it" (D). For keeping: "the controller's weakest point is catch-up speed, not step logic — a calibration answer, not a redesign" (E).

**3. Override shape.**
Options: (a) absolute one-shot with no expiry, plus immediate cancel and a hard reopen checklist; (b) absolute one-shot + expiry/max-lead; (c) bounded nudge + expiry (relative ± bps for B, C, F; A's experiment is a glide toward an exact target); plus two sub-calls — immediate vs timelocked cancel, and whether pause disarms it.
Support: (a) A; (b) D, E; (c) B, F, C as preferred form, A as a P3 simulator experiment. Immediate cancel: A, B, C vs D, E, F. Pause disarms: B, C vs A, D, E, F.
Strongest line for (a): exactness and prospectivity "are the I-bond/Treasury virtues — keep them," and treat the override like a reserved right "doctrine says almost never to use" (A). For (b): keep the exact-target semantics and the knob count (E). For (c): a nudge "cannot be forgotten into staleness and cannot be argued as fair-value setting" (F). Five of six want some expiry; A alone defends decision 28's persistence, and A is also the only one to propose allowing install before the first epoch so restarts are price-continuous.

**4. Issuance counter and run lifecycle.**
Options: (a) `setCumulativeMinted` monotonic and/or timelocked (downward only while stopped); (b) keep as-is; plus B's separate proposal for a mandatory run end and `runId`, and A's separate proposals to timelock `start`/token swap and make `canBuyNow` sticky.
Support: (a) A, B, C, E, F; (b) D. Run end: B alone; A, C, D, E, F keep no-sunset. Timelocked `start`/token swap: A, B vs C, E (D, F silent).
Strongest line for (a): "a counter that resets is a budget that isn't" (E). For (b): it "can't increase the mint budget … Bounded by `mintBudget`" (D). For a run end: on-chain mutability needs stronger accounting than an ATM because "there is no transfer agent independently maintaining sold-to-date records" (B). Against: "'no sunset' is normal program design" (F, citing the same ATM precedent). For timelocking `start`: `stop(); start(0, 1)` "turns the epoch cap into a per-block cap with no timelock" (A); against: "Stop is the asset-change ceremony" (C).

**5. The ceiling as the price control (A only, but load-bearing for A's shape).**
